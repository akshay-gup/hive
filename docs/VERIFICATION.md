# Verification

What the automated checks cover, how to run them, and what has not been verified. Hive is an alpha: this lists coverage and its limits, and does not claim that every planned capability is complete.

## Separate Routines navigation — 2026-10-29

Routines has its own screen beside Goals in the desktop sidebar and phone navigation. Goals contains goal creation and milestones; Routines shows the full saved list and its existing detail sheet/actions. Chat's “View routine” button goes to Routines. Guest navigation remains limited to Chat. The new page includes loading, empty and retry states, and phone tabs expose their selected state on the web.

Validation: all 211 mobile helper tests passed, with mobile and production-source typechecks. A fixture using the real workspace shell, sidebar, header, board provider and goal/routine components passed 50 browser checks at desktop, tablet and phone sizes, plus a 320 px width check. Checks covered separate lists, all six routine rows, the goal creation form, pause/run actions, detail sheets, browser Back, empty/loading states, recovery after an error and guest navigation. The layout detector reported no findings, the independent layout review found no material defects, and the browser console was clean. No model calls were used.

## Kernel watch: `/etc/hive` secrets and work folders — 2026-10-29

The kernel watch now also notes reads of `/etc/hive/workspace.json`, `tunnel-token`, `update-token` and the saved settings files, and of anything under `owners/`. Not passed on: the supervisor (its pid is in `/run/hive/supervisor.pid`), process 1 and the service manager's own process, the agent's process for `owners/` (its file tools are read from each call), and a process whose working folder is the same channel or person folder as the file it reads. The server marks a work-folder read against the run whose folder the reader worked in, only if the file is outside that run's folder; a work-folder read by something not working in any run's folder is no one's and is dropped. Checked by `tests/kernel-watch.test.ts`, `tests/kernel-reader.test.ts` and `tests/workspace-image.test.ts` with stand-in audit logs. **Not verified on a real machine:** how many events an install makes in a work folder (the audit system's `lost` count flags it if the kernel drops any), and the unit restart order at boot.

## Shared board lookups in channel chat — 2026-10-29

Public and private channel runs can look up tasks, projects, goals and routines with `read_board`, by words, kind or exact id. The chat service checks every current channel reader, including unjoined readers of public channels and named guests. Project viewers may read; an admin asking does not override another reader's access. An item is excluded if any reader cannot see it, including personal entries outside a sole-reader channel, narrower private scopes, unknown projects and hidden linked task/goal details. Existing routine listing uses the same check. Personal tickets and leased task workers keep their existing actor access; DMs remain excluded.

Results are bounded, paginated summaries. Machine state, signed file addresses and private routine wake locations are omitted. Access changes during a lookup refuse it; changes to exposed resources or the channel audience stop stale streamed/final replies and clear their tool steps. Persistent access generations survive room restarts and require a new model session for the next run after such a change. This does not erase earlier channel messages or provide a filesystem sandbox.

Source and affected-test typechecks passed. Tests cover guests, public readers who did not join, viewer roles, hidden exact ids, linked-item filtering, Unicode response budgets, scope changes, lookup races, room restart, stale replies, session rotation and unchanged personal/worker access. Live staging passed 16 checks through real Worker endpoints and a stand-in runner, including all four kinds, audience expansion and mid-run revocation. The isolated workspace was purged. ## Agent activity in the bell — 2026-10-29

Owners and admins get one current notification for all significant, unreviewed agent flags. Further flags update the same item and its count. It links straight to Agent activity, which also refreshes live. The notification contains no command, file path, channel or asker details. Ordinary members and guests receive neither the item nor its live events.

Reading the bell item does not review warnings. Read and dismiss state is personal; a new significant warning makes the same item unread again. Low-severity flags and partial reviews do not reset that state. Reviewing all warnings, or pruning the remaining warnings, removes the item. Existing stored flags are summarized without needing a new report, and role changes apply on every read. There is one stored read/dismiss state per person, rather than a notification history per flag.

Validation: 48 focused service, realtime and mobile helper tests passed, with changed-source/test and mobile typechecks. The browser fixture used the real notification provider, inbox, activity panel and local chat service. Desktop and 375 px phone checks passed for one row and one unread count, click-through, reading without reviewing, live updates and clearing after review. The older notification sheet also opens the same panel; the scoped visual review returned ship with no material fixes. Live staging used a stand-in runner and real owner/admin/member/guest WebSockets: 20 warnings produced one item, only owners/admins received live updates, and read/dismiss/review behavior held. The isolated workspace was purged. No model calls were used.

## Private-channel tasks — 2026-10-29

Private-channel mentions can stage human tasks through `create_issue`. The room keeps the pending choice; the asker chooses a project and reviews named people outside the channel before sharing. Other channel members cannot see the asker's project choices or approve for them. The same picker is available from a private-channel message. DMs remain excluded, and chat board-reading tools remain off.

Sharing consent is remembered per asker, project and thread, and changes to either audience invalidate it. The service rechecks access and the displayed audience before creation. Concurrent confirmation creates one task; cancellation, expiry, deleted messages, archived channels, lost access and task limits cannot leave unintended work or consent. Finished runs leave the picker usable while the machine sleeps; failed or stopped runs cancel it. Later agent handoff does not automatically copy private discussion into a project task. Versioned reply metadata lets older apps fall back to plain text for the new card.

Validation: 117 affected service, runner and mobile tests passed, with source/changed-test and mobile typechecks. The real-component browser fixture checked desktop and 375 px phone layouts, project selection, named audiences, description expansion, retry, stale-review rejection and actor-only fetching. The scoped visual review's single correction (expanding short multiline descriptions) passed its final review. Live staging used real Worker endpoints and a stand-in runner: pending choices survived disconnect, concurrent approval created one manual task, changed audiences rejected old approval, and DMs had no picker. The isolated workspace was purged. No model calls or real Google account were used.

## Ideas in chat — 2026-10-28

Saved ideas and their decisions now live in the room's scoped entries, alongside goals and routines. The machine generates shared-mail suggestions and retains only pending delivery records. Existing machine ideas transfer on reconnect, with their dates, decisions and channel scope preserved; old rows are deleted only after acknowledgement. Shared-mail suggestions are for non-guest team members. Private entries follow the same scope rules as other entries, including no admin access to personal entries.

Acceptance commits the task, goal and decision together. Concurrent acceptance creates one task; dismissal, replay, a full task cap or an interrupted write cannot leave duplicate or partial work. An interrupted old acceptance reuses its task and goal. A project's ideas go with its goals and routines when the project is deleted, and the app includes them in its deletion warning. Acceptance refuses a project with a wider audience than the idea. A personal or channel idea requires a suitable project.

Validation: 303 affected cloud, server and mobile regression tests passed, followed by targeted rollback and full runner delivery/acknowledgement checks. Production source, changed test and mobile typechecks passed in batches. A browser fixture using the real app provider verified cloud reads, accept/dismiss routing, live entry updates, and ignoring stale machine ideas, with the machine both unavailable and available. Live staging used real Worker endpoints and WebSockets with a stand-in runner: records and decisions remained available after disconnect, replay preserved decisions, private scopes held, concurrent acceptance created one goal/task, and project deletion removed scoped ideas. No model calls or real Google account were used; the temporary workspace was purged.

## Live limits check — 2026-10-28

Checked against the deployed chat and control services using existing test accounts and temporary private projects and a channel:

- At 98 open tasks, eight concurrent creates admitted two and refused six. The 101st task returned 409. Reopening and retrying also return 409 at the cap; completing a task frees a slot. Another person's allowance remains available.
- Task titles (160 characters), descriptions (12,000), notes (4,000), project names (80), project descriptions (500), channel topics (250), and messages (40,000) accepted their boundary and refused one character beyond it. ASCII and emoji message posts and edits round-trip intact. A rejected edit leaves the saved value intact.
- On a persistent connection, chat admitted 600 requests and returned 429 on the next. Sign-in returned 429 after 21 wrong-passphrase attempts. Existing control sessions and another chat account remained usable; both limits recovered automatically. Parallel bursts can overshoot: these [Cloudflare counters are approximate](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

An isolated staging workspace with a stand-in runner, without model calls, admitted eight runs for one person and refused the ninth, then stopped the workspace at 60 admitted runs. Sixty rejected retries did not consume teammates' allowances. Quota expiry is covered with a test clock rather than waiting an hour live. The live web app rendered a 40,000-character emoji message at 1400 px and 375 px without horizontal overflow or runtime exceptions.

Regression tests cover reopening by status edit, retry, note, assignment and delegation, including changes made by someone other than the creator. Refused requests cannot extend run quotas; a run stopped after dispatch still counts. The affected suite passed 83 tests; production source and changed test typechecks passed separately.

The checks found and fixed three gaps: reopening bypassed the task cap, refused runs consumed quotas, and message posting counted emoji differently from editing. All temporary projects, tasks, channels, staging workspaces and the binding probe Worker were removed. Open-ended workflow input metadata was also observed to accept a request above 256 KiB; this work adds no global JSON body budget. Native keyboard behavior and sustained load across multiple Cloudflare locations were not tested.

## The agent under test

Hive's agent is OpenCode. Chat and tasks are tested through Hive's own run translation, event bus and tool bridge, with two stand-ins for `opencode serve`:

- an in-process stand-in (`tests/helpers/opencode.ts`) that plays the agent's side of a task, and
- a fake OpenCode HTTP server (`tests/helpers/fake-opencode.ts`) that speaks the protocol Hive's SDK client uses: health and version, sessions, prompts, the global event stream and tool registration. Its agent calls Hive's tools over HTTP, as OpenCode does.

A real `opencode serve` was also run without a model, to check the protocol these imitate: health and version, sessions, the event stream, tool registration, and the shape of errors and tool events. No check has run a model, so nothing here shows how a real model uses Hive's tools.
